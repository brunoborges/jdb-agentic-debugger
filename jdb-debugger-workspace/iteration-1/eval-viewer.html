NEW skills/jdb-debugger/scripts/jdb-interactive.py
Event-driven JDB session driver (349 lines). Replaces the previous sleep-based timing approach with true I/O-event-driven execution. Key responsibilities:
  • Spawns JDB as a subprocess and streams output through a background reader thread with proper partial-UTF-8 decoding.
  • Waits for specific output patterns (breakpoint set confirmation, breakpoint hit, stack frames, thread-not-suspended) before advancing to the next command — eliminating all race conditions caused by fixed sleep delays.
  • Detects overloaded-method breakpoint errors, auto-runs methods <Class>, extracts all matching signatures, and prints actionable [WARN] + [HINT] messages with ready-to-paste --bp examples.
  • In attach mode: blocks after setting breakpoints until a Breakpoint hit event is received, then executes post-breakpoint commands in the correct suspended-thread context.
  • Intercepts run in attach mode (skips it silently with an [INFO] explanation) and adds a [WARN] explanation when where is called after cont has already resumed the thread.
  • Adds a [INFO] preamble before where all explaining the suspend=n JDWP limitation and recommending plain where.
  • Accepts a JSON config file (generated by the shell wrapper) so the driver is fully decoupled from argument parsing.
NEW tests/scenarios/AttachDemo.java
Dedicated test scenario for attach-mode pain-point validation (68 lines). Designed to reproduce all four pain points in a single runnable program:
  • Provides three overloaded process() variants to trigger the "already overloaded" error (Pain 1).
  • Exposes a handleRequest() method as the primary breakpoint target — no overloads, predictable suspension behaviour (Pain 2, 3, 4).
  • Runs a while(true) loop with a 2-second delay so the target JVM stays alive long enough to attach, set breakpoints, and wait for hits.
  • Launch command: java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:15005 AttachDemo
MODIFIED skills/jdb-debugger/scripts/jdb-breakpoints.sh
Substantial rewrite of the batch execution path and help text. Key changes:
  • Added SCRIPT_DIR resolution so the script can locate jdb-interactive.py regardless of the working directory from which it is called.
  • Replaced the old sleep-based batch engine (custom timeout loop + background PID management) with a thin JSON config generator that delegates to jdb-interactive.py when Python 3 is available; the old sleep-based path is preserved as a fallback with a clear warning.
  • Cleaned up --auto-inspect to avoid prepending run in attach mode — the event-driven driver handles JVM-start detection internally.
  • Rewrote the help text: removed obsolete environment-variable timing knobs (JDB_BP_DELAY, JDB_RUN_DELAY, etc.) and replaced them with an ATTACH MODE GUIDE section covering overloaded methods, where vs where all under suspend=n, and the JDWP single-connection limit.
  • Simplified the sleep-based fallback code path to remove the complex nested PID-management timeout loop, replacing it with a straightforward run_batch | timeout … jdb pipeline.

Batch Mode Race Condition — "No Current Thread" After cont
File: jdb-interactive.py · post_cmd handling · lines 323–335
🔴 How to Reproduce (Baseline)

The old driver used fixed sleep delays. In attach mode with suspend=n, the thread is only suspended during a breakpoint hit. Sending where after cont (with only a 0.5 s delay) races against the JVM resuming the thread, resulting in "No current thread":

# Old skill — sleep-based batch bash skills/jdb-debugger-snapshot-baseline/scripts/jdb-breakpoints.sh \ --host localhost --port 15005 \ --bp "stop in AttachDemo.handleRequest" \ --cmd "where" --cmd "cont" --cmd "where" --cmd "quit" --timeout 15 Breakpoint hit: "thread=main", AttachDemo.handleRequest(), line=41 bci=0 main[1] > No current thread. ← where fired before thread suspended > Breakpoint hit: "thread=main", AttachDemo.handleRequest(), line=41 bci=0 main[1] [1] AttachDemo.handleRequest ... ← accidental second hit
🔵 Fix Applied (new driver)

The event-driven driver waits for the Breakpoint hit event pattern before sending the first post-breakpoint command. After cont, it again waits for either the next hit or a prompt — so commands always execute in the correct JVM state. If where is issued after cont and the thread is no longer suspended, an explanatory [WARN] is printed rather than a silent failure:

# New driver — event-driven [INFO] Attach mode: waiting for breakpoint to be hit... [INFO] Trigger the action in the target JVM now. Breakpoint hit: "thread=main", AttachDemo.handleRequest(), line=41 bci=0 send> where [1] AttachDemo.handleRequest (AttachDemo.java:41) [2] AttachDemo.main (AttachDemo.java:61) send> cont send> where No current thread. [WARN] Thread not suspended here. In attach/suspend=n mode, 'where' only works right after a breakpoint fires. Avoid inserting 'cont' before 'where' — cont resumes the suspended thread.

Spurious "run" Command in Attach Mode Breaks Command Sequencing
File: jdb-interactive.py · post_cmd handling · lines 311–315 · jdb-breakpoints.sh · lines 157–159
🔴 How to Reproduce (Baseline)

When --auto-inspect is used, the old shell prepended a run command to the post-command list unconditionally. In attach mode, run does nothing (the JVM is already running), but it still consumes a prompt cycle. This shifts all subsequent commands out of sync with the JVM state, producing cascading "No current thread" and "No default thread" errors:

# Old --auto-inspect in attach mode injects "run" unconditionally bash skills/jdb-debugger-snapshot-baseline/scripts/jdb-breakpoints.sh \ --host localhost --port 15005 \ --bp "stop in AttachDemo.handleRequest" \ --auto-inspect 1 Breakpoint hit: "thread=main", AttachDemo.handleRequest(), line=41 bci=0 main[1] > ← "run" consumed here, no effect Breakpoint hit: "thread=main", AttachDemo.handleRequest(), line=41 bci=0 main[1] [1] AttachDemo.handleRequest ... main[1] Local variable information not available... main[1] > No current thread. > No default thread: please use the "thread" command first.
🔵 Fix Applied (new driver)

Two complementary fixes were applied:

  • Shell-side (jdb-breakpoints.sh): run is only prepended to POST_CMDS when IS_ATTACH == false. Attach mode never injects run.
  • Driver-side (jdb-interactive.py): If a run command is encountered in the post-command list while is_attach=true, it is silently skipped with an [INFO] message — a safety net in case callers build the config manually.
# New driver — run is skipped, subsequent commands work correctly Breakpoint hit: "thread=main", AttachDemo.handleRequest(), line=41 bci=0 [INFO] Skipping 'run' in attach mode (JVM is already running). send> where [1] AttachDemo.handleRequest (AttachDemo.java:41) [2] AttachDemo.main (AttachDemo.java:61) send> quit [JDB session complete]
